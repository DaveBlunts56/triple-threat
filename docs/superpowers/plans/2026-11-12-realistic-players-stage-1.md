# Realistic Players, Stage 1 (The Early Look) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One generated, dressed, rigged player with five motion-capture motions is drawn in place of all six capsules, on this computer and in the Chromebook's single file, so the owner can judge the look before nine more are made.

**Architecture:** Scripts under `tools/blender/` run inside Blender and build `assets/players.glb`, `assets/motion.glb` and `assets/motion.json`. The game finds those files through `src/render/assets.js`, chooses each player's leg motion with a pure function in `src/render/motion.js`, and plays it with a Three.js animation mixer in `src/render/people.js`. `tools/single-file.mjs` packs the files into the single HTML.

**Tech Stack:** as milestones 1 and 2, plus Blender 4.5.16 with the MPFB 2.0.18 extension, driven through the Blender MCP; `GLTFLoader` and `SkeletonUtils` from `three/addons/` (already in `node_modules`).

**Spec:** `docs/superpowers/specs/2026-11-12-realistic-players-design.md`

**Branch:** `feat/realistic-players`

**Scope:** this plan covers item 1 of the spec's "Order of work" only. The spec makes the owner's verdict on the early look a gate: stages 2 to 4 get their own plan after it, when Mixamo's catalogue and the pipeline's real behaviour are known.

## Decisions the spec leaves open

- **Blender version:** 4.5.16 (`blender-4.5.16-linux-x64.tar.xz`, 377,826,288 bytes, from `download.blender.org/release/Blender4.5/`), installed beside 4.0.2 under `~/.local/opt/` with the launcher `~/.local/bin/blender-4.5`. It is the newest 4.x; 5.3.0 came out two days before this plan and MPFB states no upper limit, so the older line is the safer first try.
- **Which body goes to Mixamo:** the documented MPFB route. One "reduced doll" of the stage 1 player is uploaded by the owner, and every clip is downloaded for that doll. The other nine reuse the clips by bone name; MPFB warns that a very different shape "will look strange", which stage 2 checks.
- **Gait bands, not gait blending:** a player's legs play one of idle, walk, run or sprint chosen by speed, at the rate that matches his real speed, and cross-fade over 0.15 s when the choice changes. Players reach full speed in under 0.2 s, so two gaits blended by weight would never be seen.
- **Stage 1 shows the one player six times,** tinted by team, so he is seen running, jumping and being substituted in a real match.
- **Stage 1 has one quality level.** The corner label gains the frame rate now, because the owner has to report it from the Chromebook; the High and Low levels come in stage 2.
- **Jersey, shorts and shoes are generated by script** from the body mesh (regions lifted off the skin and shaped), so no hand-edited `.blend` has to be stored. If MPFB's CC0 "Shoes 01" pack has a usable sports shoe, it is used instead of a generated one.

## Review Focus

Conditions the spec implies but does not spell out, most likely first. Each has a test or a stated check in the task named.

1. The model files are missing or broken (a fresh checkout, a failed export): the game still starts and plays with capsules, with one warning in the console. (Task 6)
2. A player who is in the air while still moving sideways: his legs show the jump, never a run. (Task 3)
3. A speed that sits on the edge between two gaits, or a tired player whose sprint is slower than a fresh player's run: the legs do not flicker between two clips. (Task 3)
4. The game is paused, or the tab is hidden, for a long time: the motion does not fast-forward when play resumes. (Task 6)
5. The single file is built while a model file is missing: the build stops and names the file, instead of producing a file that silently has no players. (Task 2)

### Task 3: Which leg motion a player shows

**Files:**
- Create: `src/render/motion.js`, `tests/motion.test.js`

**Interfaces:**
- Consumes: `PLAYER.jumpV`, `BALL.gravity` from `src/sim/tuning.js`.
- Produces:
  - `AIR_TIME`: seconds a jump lasts, `2 * PLAYER.jumpV / BALL.gravity`
  - `MOTION`: frozen `{ idleBelow: 0.3, walkBelow: 2.2, runBelow: 5.6, stick: 0.2, minRate: 0.6, maxRate: 1.5, fade: 0.15 }`
  - `legMotion(player, gaits, last = null) → { clip, rate } | { clip: 'jump', at }`. `player` needs `vx, vz, y, vy, jumpT`. `gaits` is `{ walk, run, sprint }` in metres per second (from `motion.json`). `last` is the clip he showed on the previous frame. `at` runs from 0 at take-off to 1 at landing.

- [ ] **Step 1: Write the failing tests**

```js
const gaits = { walk: 1.5, run: 4, sprint: 6.5 };
const still = { vx: 0, vz: 0, y: 0, vy: 0, jumpT: 0 };
const clip = (speed, last) => legMotion({ ...still, vx: speed }, gaits, last).clip;

test('standing is idle; moving is a walk, a run or a sprint by speed', () => {
  assert.deepEqual([0, 0.2, 1, 2.1, 2.3, 5, 5.5, 5.95, 7].map(v => clip(v)),
    ['idle', 'idle', 'walk', 'walk', 'run', 'run', 'run', 'sprint', 'sprint']);
});

test('the clip plays at the rate that matches his real speed, within limits', () => {
  assert.equal(legMotion({ ...still, vx: 5 }, gaits).rate, 1.25);          // 5 / 4
  assert.equal(legMotion({ ...still, vx: 2.3 }, gaits).rate, 0.6);         // 2.3 / 4 is 0.575: held at the slowest rate
  assert.equal(legMotion({ ...still, vx: 3, vz: 4 }, gaits).rate, 1.25);   // speed is the length of the velocity
  assert.equal(legMotion(still, gaits).rate, 1);
});

test('in the air the legs follow the jump, whatever his speed', () => {
  assert.deepEqual(legMotion({ ...still, vx: 5, y: 0.5, vy: 1, jumpT: AIR_TIME / 2 }, gaits), { clip: 'jump', at: 0.5 });
  assert.equal(legMotion({ ...still, y: 0.1, vy: -3, jumpT: 5 }, gaits).at, 1);      // never past the landing
  assert.equal(legMotion({ ...still, vy: 4, jumpT: 0 }, gaits).clip, 'jump');        // the step he leaves the floor
});

test('near the edge between two gaits he keeps the one he is in', () => {
  assert.deepEqual([clip(5.7, 'run'), clip(5.85, 'run')], ['run', 'sprint']);
  assert.deepEqual([clip(5.5, 'sprint'), clip(5.3, 'sprint')], ['sprint', 'run']);
  assert.deepEqual([clip(0.4, 'idle'), clip(0.2, 'walk')], ['idle', 'walk']);
  assert.equal(clip(5.25, 'run'), 'run');                                           // a tired sprinter: no flicker
});

test('a jump always ends in the gait his speed calls for', () => {
  assert.equal(clip(5, 'jump'), 'run');
});
```

- Produces:
  - `export_mixamo_doll.py`: makes MPFB's "reduced doll" of the stage 1 player and writes `assets/source/mixamo-upload.fbx`.
  - `build_motion.py`: imports each FBX, makes the player's own skeleton follow it, bakes the result onto that skeleton, and writes `assets/motion.glb` (the skeleton and five animations, no meshes) and `assets/motion.json`.
  - Clip rules: 30 frames a second. `idle`, `walk`, `run` and `sprint` loop, with the last frame equal to the first, and play on the spot (the hips keep their up-and-down and side-to-side movement but do not travel). `jump` covers exactly the time both feet are off the floor, and its hips do not rise: the game lifts the whole player.
  - `motion.json`: `{ "gaits": { "walk": n, "run": n, "sprint": n }, "clips": { "<name>": { "duration": seconds, "loop": bool } } }`. A gait's number is the speed the clip travelled at before it was put on the spot, in metres per second.
